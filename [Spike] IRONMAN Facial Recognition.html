03
Engineering

Technology

Face — what it does

The scanned QR says who the athlete claims to be; the camera confirms the live face matches the one they registered. A real gate — if it fails, that route closes and they scan their ID instead. Calibrated like a building entrance, not a bank: staff are present and a failure costs a few seconds, not money.

ID scan — what it does

Reads name, date of birth and document number straight off the document and matches them to the registration. It does not verify the document is genuine — it replaces manual typing and volunteer eyeballing, which is the same level of checking that happens today.

Camera — used by both paths
react-native-vision-cameraOne camera layer for face and documents alike.
react-native-vision-camera-face-detectorML Kit face detection on the live feed, guiding framing in real time during setup and check-in.
Face matching — phase 1, cloud
AWS Rekognition CompareFacesOne call through our backend compares the live face against the registered one and returns a similarity score.
Trade-offHigh accuracy, negligible cost per check, simple to build. Needs internet and takes 1–3 seconds.
Face matching — phase 2, on device
MobileFaceNet via react-native-fast-tfliteEvent faces converted to numeric codes and loaded onto the device beforehand. Under 1 second, works without venue wifi.
Same screensIdentical flows — only the speed changes. Only worth doing if queues or connectivity prove to be a problem.
ID scan — one screen, two readers
ML Kit Barcode + aamva-parserReads the barcode on the back of US and Canadian licences. Mandatory on those documents and already contains every field, so it is more reliable than reading printed text.
ML Kit Text Recognition + mrzReads the coded lines at the bottom of passports and international IDs. Built-in check digits confirm the read was correct.
On device, offline, no cost per scanBoth readers run at once and identify the document automatically. Nothing from the document reaches a third party.
Phase 1 — build this
Cloud matching, iPads
Simplest working version. No face data stored on any device, one backend integration. The 1–3 second wait is fine at expo pace as long as the screen shows progress.
Phase 2 — only if needed
On-device matching
Buys about two seconds per athlete and removes the wifi dependency. Worth it only if queues or venue connectivity turn out to be a real problem — it means loading face data onto devices, which needs its own safeguards.

What it takes to run

Hardware

The proposal is an unattended screen the athlete uses alone — putting a volunteer behind it removes most of the benefit. But that screen can start as an iPad IRONMAN already owns.

Phase 1 — no hardware purchase

iPads already in use

  • iPad existing
  • Floor or table stand, lockable buy
  • Power and cable management venue
  • Wifi or mobile data venue
  • Front camera — face built in
  • Rear camera — ID scan built in

Proves the flow at real races before anyone commits budget. Bib numbers shown on screen and sent to the app instead of printed.

Phase 2 — if it proves out

Dedicated totem

  • Purpose-built kiosk enclosure buy
  • Camera at fixed height buy
  • Thermal printer for slips buy
  • Outdoor-readable screen buy
  • Weather and dust protection buy
  • Floor mounting or ballast buy

Better in sunlight, harder to walk off with, and prints a slip. Real investment — worth deciding after phase 1 numbers exist.

Also needed, both phases

Around the check-in point

  • Staff device for the picking queue existing iPad
  • Screen at the collection counter existing iPad
  • Help desk console laptop
  • Backup: staffed lane always open staff

Camera height matters at both phases — it has to work across a wide range of athlete heights and seated positions. Easier to solve with an adjustable stand than a fixed totem.

Only if on-site registration ships

Taking payments

  • Certified card reader buy
  • Payment provider contract contract
  • Security certification process process
  • Separate from the tablet required

Why separate hardware: if card data touches our software, our entire system falls under payment industry certification — every server, every log, audited annually. A certified reader encrypts the card at the moment of tap and talks to the payment provider directly, so our app only ever sees approved or declined. That certification process, the reader per station and the provider contract are why this is the largest single cost in the proposal, serving only flow 07.

05
Needs confirming with counsel

Where face data is regulated

Face data is treated as sensitive personal information in many places, with real requirements attached. The ID scan path is not affected — reading fields without keeping the image is not regulated the same way. Nothing here is legal advice; IRONMAN's lawyers confirm per race.

Strictest

Illinois

Written permission before collecting, and a published schedule for destroying the data. Individuals can sue directly, with set damages per person. A large field makes the exposure significant if the process is not followed exactly.

Check before deploying

Texas · Washington

Both require informed permission before capturing face data for commercial use. Enforced by the state rather than by individuals, but the permission requirement is the same.

Check before deploying

European Union

Face data is a special category requiring explicit permission, and a formal impact assessment must be completed before launch. Additional rules apply depending on how the matching works, which is why we confirm identity one-to-one rather than searching a database.

Check before deploying

Brazil

Sensitive data requiring freely given permission. A recent court ruling confirmed face recognition cannot be the only way in — an alternative must always be offered. National rules are still being finalised.

Lower risk

Everywhere else

Around twenty more US states cover face data under general privacy laws, and most countries have some form of sensitive-data rule. Confirm per race calendar rather than assuming.

Not affected

The ID scan path

Reading name and date of birth and discarding the image is not biometric data. It works the same way in every country, which is why it is the path everyone can use.

Applies everywhere, regardless of jurisdiction

  • Permission is asked on its own screen, never bundled with terms or the race waiver
  • A numeric code is stored, not the photograph — the code cannot be turned back into a face, so a data breach exposes no usable image of an athlete, and it keeps only what is needed to answer "is this the same person"
  • Data is destroyed on a published schedule — this has to be defined and actually happen, not just stated
  • Athletes can delete their data at any time
  • A non-face way in is always available — never the only option
  • Face setup is 18 and over only
  • Data collected for check-in is not reused for anything else without asking again
  • The feature can be switched off per race where the rules require it
06
Before building

To decide

How close a face match counts as a match
Set it too strict and athletes who genuinely are themselves get sent to the ID scan. Set it too loose and the wrong person could collect a bib. With staff nearby, we would rather be too strict. Suggest tuning it at smaller races before any large event.
Does the athlete app have accounts we can attach a face to?
Face setup at registration assumes the athlete has an account the data can live on. If registration today is mostly email confirmations, that needs building first.
Who defines the destruction schedule, and what is it?
A published timeline for deleting face data is a legal requirement in several places, not a nice-to-have. Needs an agreed number — after each race, after a season — and someone confirming it actually happens.

On-site registration and payment · dedicated totem hardware · on-device face matching · transition access on race morning · measuring how long check-in takes today, so improvement can be shown rather than assumed.
